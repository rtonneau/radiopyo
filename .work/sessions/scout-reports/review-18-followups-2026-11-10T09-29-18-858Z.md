# Ticket 18: follow-up findings

Each finding was re-checked against the code at the end of the session (branch
`refactor/readability-and-jacobian-prep`, base a09d989). None was found already fixed.

## F1: Analytic Jacobian is missing (High)

- Files: `radiopyo/simulation/ode_functions_solver.py`, `radiopyo/simulation/unit_cell.py` (`_raw_run`), `radiopyo/utils/sim_types.py`.
- The old `jacobian()` was removed (stale signature, 4-D `JRki` tensor). `UnitCell.run(use_jac=True)` and the chunked runs raise `NotImplementedError`, so LSODA/BDF always use finite differences.
- Fix: write the Jacobian on top of `reaction_rates` and `SimMatrices` (`KMatrices` gather indices, `GVector`, `EzMatrices`), as a sparse/vectorised `J = S_k @ diag(dr/dy)`; validate it against a finite-difference Jacobian of `derive` in a test, then wire `use_jac` to `solve_ivp(jac=...)`.

## F9: Enzymatic reactions ignore the negative-product (depletion) flag (Medium)

- Files: `radiopyo/simulation/ode_functions_solver.py` (`michaelis_menten_rates`), `radiopyo/simulation/environment_build.py` (`make_enzymatic_matrix`), `radiopyo/utils/sim_types.py` (`EzMatrices`).
- `negative_product_block` only looks at `KMatrices.negative_products`; the enzymatic matrix does not carry the flag (`ope`). A Michaelis-Menten reaction with a "negative" product keeps running when that species is depleted, unlike k-reactions. Deferred by the user to the Jacobian work (ticket 17).
- Fix: add a `negative_products` array to `EzMatrices`, apply the same block in `reaction_rates`, and handle it in the Jacobian (F1) so both stay consistent.

## F2: `_scale_factor` dose-rate fit has no range check (Medium)

- Files: `radiopyo/utils/g_values.py` (`GValuesBoscolo._scale_factor`), `radiopyo/simulation/unit_cell.py` (`change_LET`, `variable_GValues`).
- `0.97207704 * dose_rate**-0.10972` is applied to every G-value with no valid range: it is `inf` at 0 Gy/s (`_scale_factor(0.0)` returns `inf`), 2.07 at 1e-3 Gy/s and 0.17 at 1e7 Gy/s. With `variable_GValues = true` and a beam of zero peak dose rate, the G-values become infinite.
- Fix: document the fitted dose-rate range (from the Blain data), clamp or raise `ValueError` outside it, and refuse a non-positive dose rate.

## F3: H2O initial concentration polynomial rises with temperature (High)

- Files: `radiopyo/chemistry/species.py` (`H2O`, ~line 389), `radiopyo/simulation/environment_build.py` (fixed-species vector).
- `cc_init=[55.50, 6.075e-3, 4.110e-4, 1.496e-6, 2.619e-9]` (all positive, T in degC) gives 55.50 M at 0 degC, 55.93 M at 25 degC, 57.03 M at 50 degC and 59.49 M at 80 degC. The density of water gives about 55.35 M at 25 degC and falls with temperature (about 53.9 M at 80 degC), so the sign of the temperature terms looks wrong. Since ticket 13 this value follows the simulation temperature, so every rate involving H2O (e.g. `e_aq + H2O`) is affected away from 25 degC.
- Fix: find the source of the coefficients, compare with a density table (CRC / IAPWS), fix the sign or the variable (K vs degC), and add a test of the concentration at 4, 25 and 80 degC. Any change moves 25 degC results by about 1%: regenerate goldens with approval.

## F4: `Timer.time_till_next_OFF` returns NaN for continuous timers (Medium)

- Files: `radiopyo/physics/timer.py` (`BaseTimer._phase`, `Timer.time_till_next_OFF`), `radiopyo/physics/beam.py` (transition generator, line ~308).
- For `ConstantBeam` and `SinglePulseBeam` the timer has `period = inf`; `_phase` computes `period * period_index` as `inf * 0 = nan`, so `Timer.new_constant(...).time_till_next_OFF(t)` is NaN (checked: `ConstantBeam(1).timer.time_till_next_OFF(1.0)` and the `SinglePulseBeam` timer both give `nan`). The generic `make_matrix` avoids it with an `isinf(period)` branch, but any other caller gets NaN.
- Fix: in `_phase`, return `time - start_time` when the period is infinite (and make `time_till_next_OFF` return `on_time - phase`); add tests for constant and single-pulse timers.

## F5: `SimEnv.make_hash` always raises `TypeError` and is not seed independent (Low)

- Files: `radiopyo/simulation/environment_build.py` (`make_hash`, line ~256).
- `frozenset(self.parameters.items())` fails because `parameters["species_order"]` is a dict (`TypeError: unhashable type: 'dict'`, verified on the pure-water config). Even without the dict, `repr(frozenset(...))` depends on `PYTHONHASHSEED`. No caller exists; `pyproject.toml` excludes `def make_hash` from coverage.
- Fix: hash a canonical serialisation (`json.dumps(..., sort_keys=True, default=str)` of parameters and initial concentrations) or remove the method.

## F6: `.strip(".sim")` strips characters, not a suffix (Low)

- Files: `radiopyo/simulation/persistence.py` (`parse_dataset_name`, line ~297).
- `"x.sim".strip(".sim")` removes any of the characters `.`, `s`, `i`, `m` from both ends, so a name part ending or starting with those letters (e.g. a key like `...__LET_2.5__dose_10.sim`, or a name starting with `m`/`s`/`i`) is mangled.
- Fix: `removesuffix(".sim")` (Python 3.9+). Check that names already stored in HDF5 files parse the same, and keep the old-file read test green.

## F7: `burst_dose_rates` is not persisted to HDF5 (Medium)

- Files: `radiopyo/simulation/ode_result.py` (`_burst_dose_rates`, `to_json_config`, `from_json_config`), `radiopyo/simulation/persistence.py`.
- A result read back from a file has `burst_dose_rates = None`, so `integrate_production_of` falls back to "one burst per beam pulse at the peak dose rate", which is wrong for chunked runs where the burst count differs (or `use_beam=False`). Documented in the CHANGELOG.
- Fix: store the list in the json config (new optional key, absent in old files -> keep the fallback) and restore it in `from_json_config`.

## F8: `reconstruct_reactions` uses the result beam even when `use_beam=False` (Medium)

- Files: `radiopyo/simulation/ode_result.py` (`reconstruct_reactions`), `radiopyo/simulation/unit_cell.py` (`run`, `SimChunksIter`).
- `ODEResult` is built with the current beam and does not remember `RunOptions.use_beam`; the recomputed radiolytic rates show the beam's dose rate for a run that was integrated without the beam (noted in ticket 12 and left as is).
- Fix: record `use_beam` on the `ODEResult` (and persist it, see F7) and pass `beam=None` to `reaction_rates` when it is False.
